## 4. S4 多工具条件编排 + 操作确认与回放

**目标**：兑现方案核心差异化「工具调用 —— 单次调用独立返回 → 多工具编排 + 条件分支 + 主动建议」。

**范围**

- `grader` 节点 + `add_conditional_edges`：条件分支，同时支持硬编码阈值与 LLM 判断两种模式
- 中间结果在 State 的 `tool_results: dict` 累加（接入点已预留，见 `mvp-design.md:361`）
- 工具失败降级：Tool Executor 统一 try-catch 写 `error`，`grader` 检测到后走降级分支，**已成功的结果不被丢弃**
- `recursion_limit` 截断，超限返回当前结果而不是挂死
- `POST /confirm` 操作确认：写类操作执行前返回确认卡，用户点确认才继续（接入点 `mvp-design.md:365`）
- `POST /replay` 操作回放：按 `tool_calls.steps_json` 重放上次执行的节点序列与每步参数/耗时，供调试与面试演示
- 新增一个**写操作 API**（首个候选：补考报名提交），承接方案"表单填写"语义

**明确不做**：Page Agent iframe 注入与五级元素定位降级（见第 8 节第 1 条）、`rewriter` 节点（属 S3 的"改写器 + 校验清单"，不在本文重复定义）、多会话并发编排、跨用户编排。

**依赖**：S3 的 `query_grades`；既有 `steps_json` 埋点与 `tool_calls` 表（MVP 已交付）。

**验收（可跑、可判定）**

1. 问「查我上学期高数成绩，不及格就告诉我补考时间」→ 返回文本**同时**含分数与补考提示，并附跳转卡片；`steps` 序列含 `grader`
2. 写操作未点确认 → 不执行；无 Cookie 打 `POST /confirm` → 401
3. `POST /replay` → 返回上次的节点序列、每步参数与耗时，与 `tool_calls.steps_json` 一致
4. 让第二个工具抛错 → 返回值仍含第一个工具的成功结果 + 错误提示（降级分支被走到）
5. 构造死循环 → 被 `recursion_limit` 截断并返回，进程不挂

**估时**：~1.5 天

## 5. S5 Agent 行为测试体系（方案第七节 5 维度）

**目标**：兑现方案核心差异化「功能测试 → Agent 行为测试（5 维度量化评估）」，把方案第七节的达标线变成跑得出数字的脚本。

**范围**

| 维度 | 达标线（沿用方案第七节） | 交付物 |
|---|---|---|
| 任务完成度 | ≥ 85% | **50 条任务测试集**（信息查询 20 / 页面跳转 15 / 多工具编排 10 / 边界模糊 5）+ 跑分脚本 |
| 工具选择准确性 | ≥ 90% | 「意图 → 期望工具」映射表 + 从 `tool_calls` 取实际调用做对比的脚本 |
| 参数传递正确性 | ≥ 95% | 参数断言脚本（按每条用例的期望参数校验） |
| 执行路径合规性 | ≥ 95% | **路径异常检测脚本**：解析 `steps`，三条规则——同节点连续 >3 次 / `Router` 后直接 `Generator` / `Generator` 后回 `Router` |
| 越权防护有效性 | **100%** | **复跑越权全集 A1–A10**（A1–A6 属 S3 判据、A7–A10 已随 S1 通过），汇总进报告 |

宿主与埋点均为现成接缝：以 `mvp-design.md:367` 指定的集成测为宿主加参数化用例文件，`tool_calls` 表即埋点数据源。

**越权这一维 S5 不产出新用例**：A1–A6 已是 **S3 的验收判据**（定义见 `spec2:413–424`，且 `spec2:424` 要求它们走真 SQL 生成路径而非 mock），A7–A10 已随 S1 通过（`spec2:481`）。S5 只负责**复跑 A1–A10 全集**并把结果汇总进五维报告，达成方案的 100% 拦截线。

**Playwright E2E**：S2 计划 `:2119` 明确"严格的 UI 回归 S3 收口时用 Playwright 补"，S5 一并收口——按方案第七节第 6 小节的 8 步流程（登录 → 悬浮球 → 输入 → 等结果 → 确认卡片 → 验证跳转 → 截图留证）。

**明确不做**：RAGAS（理由见第 8 节第 3 条）、并发/压测、模型幻觉评测、非 Agent 层的单元测试覆盖率指标。

**依赖**：S4（路径合规这一维必须先有编排路径可测）。

**验收（可跑、可判定）**

1. `tests/` 下 50 条用例文件存在，分类计数为 20/15/10/5
2. 映射表 + 脚本跑出工具选择准确率数字，≥ 90%
3. 参数正确率脚本跑出数字，≥ 95%
4. 路径检测脚本对三条异常规则各自能**红**（注入一条构造的异常序列作阳性对照），正常序列绿；合规率 ≥ 95%
5. **A1–A10 全集**复跑通过，拦截率 100%（A1–A6 依赖 S3 已交付的 SQL 校验层）
6. 五条达标线汇总成一份可复跑报告
7. Playwright E2E 跑通方案第七节的 8 步流程并留截图

**估时**：~2 天

## 9. 依赖与顺序约束（风险）

- **S4 卡在 S3**：S3 未交付则 S4 的旗舰演示无法成立。这是唯一的硬依赖链，S3 不做就不该开工 S4。
- **S5 的路径合规维度卡在 S4**：没有 `grader` 就没有 `Router → ToolExecutor → Grader → ToolExecutor → Generator` 这条待测路径。其余四维（任务完成度、工具选择、参数、越权）理论上 S3 之后即可启动，但整体放在 S4 之后，避免两套测试基础设施分头建两次。
- **S7 的安全前置不可跳过**：`spec2:455` 那句告警是硬约束。明文密码 + 非 `Secure` Cookie 一旦上公网即为实际可利用的风险。
- **估时合计**：S4 + S5 + S6 ≈ 4 天，S7 另计约 1 天。S3 的 1.5 天是既有定义，不在本文估时内。
